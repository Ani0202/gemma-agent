### Row classification (frozen before any run; mechanical, from the raw timing.jsonl row)
- KNOWN-DIAG (not an error): editable_failed=True where every failing editable subprocess output contains `uninstall-no-record-file`.
  This is the documented scorer-harness RECORD strip (docs/GOLD_CALIBRATION.md v2, report 005-prelim): flat-layout rich/fastapi
  import from /workspace via cwd, and the 48-clean gold/null calibration was done in the same docker-path where it occurs. It was
  on 7/8 rows of every plan-005/006 kernel (results/kaggle_timing_31b_v00{1,3,5,6,7,8}.json). Counted and listed, never gating.
- HARNESS error (H), exactly these: H-ROW = row missing, or the row's `error` field non-null (agent_timing.py sets it only for the
  fail-closed harness_error, an evaluation/cleanup exception, or a trace-parse failure; normal agent end states such as
  timeout/turns/tool_calls/no_submit leave it null); H-SETUP = setup_failed for any reason other than KNOWN-DIAG (a fatal setup step rc != 0,
  missing_tool_deps, or an editable failure without `uninstall-no-record-file`); H-VERIFY = the row's filtered patch is non-empty
  but exit_code is not an integer in 0..5 (verification never returned a pytest exit code). vLLM not up = the
  whole kernel is void.
- Everything else is an AGENT outcome and is a quality result, never a validity question: PASS = stock resolved=True;
  FAIL sub-labels: no/empty patch (stock evaluate_task returns resolved=False, exit -1, verification not run, evaluate.py:324),
  timeout, pytest exit 1, pytest exit 2-5 (e.g. the patch breaks collection), exit 0 but resolved=False (JUnit/required nodes).

## Decision rules
- ARM 1 alone is a measurement: no ship decision follows from it. It sets the baseline for arm 2 and is cited in the dec 061 (i)
  v004 cap discussion. Arm 1 is INVALID (env problem, not a quality result) iff H rows >= 5 of 33, whatever the pass count.
- ENV CONTROL (pre-registered follow-up, not gating the runs): a gold+null pass of the 33 dev ids through this exact kernel
  verification path (CPU kernel, no GPU quota; needs a small gold-patch mode, codex-reviewed first). Until it exists, arm 1 is
  reported with the caveat "env agreement with the local gold calibration unmeasured in the kernel path". When it exists:
  ids whose kernel-path gold fails or null passes are listed and a sensitivity pass rate excludes them; the primary is unchanged.
- ARM 2 vs ARM 1 (paired, same 33 ids, k=1 FIXED: no second sample under this plan, whatever arm 2 shows): per-task discordant
  counts on-only / off-only, exact two-sided sign test. Any later k>1 needs a new pre-registration with a fixed n and seeds, fixed
  before results, and a task-level analysis (per-task mean over samples, sign test on per-task differences).
  - ON-ADOPT: on-only > off-only, p < 0.2, AND ON timeouts <= OFF timeouts + 2, AND the cap-3.5 timing check passes.
  - ON-BETTER-VETOED: on-only > off-only with p < 0.2 but the timeout or timing condition fails: keep OFF for shipping; report
    to the Director with the timing data as a candidate for a cap/budget follow-up (no automatic further arm).
  - KEEP-OFF: off-only >= on-only.
  - NO-DIFFERENCE: on ahead with p >= 0.2: keep OFF (cheaper, faster). +-3 tasks on 33 is noise.
  - Cap-3.5 timing check (cap unchanged, so this checks that thinking does not break cap enforcement): every ON row has a non-null
    agent_clock_seconds <= 3.5 x 60 + 10 = 220 s and finalization_seconds <= 30 s; any violation or null fails the check.
- Cost note: verification adds a fresh sandbox setup per task (Container B, two dependency installs), so per-task wall is higher than
  the plan-005 screens (~5.5 min/task); the smoke measures it. If arm 2 at k=1 does not fit next week's quota with other approved work,
  the arm-2 schedule comes back to the Director with the measured numbers.
