## Feasibility (dec 070 item 1): what a bundle can configure, in the harness the scorer runs (swegemma 0.2.11, adk_submission, source-read on this VM)
Tool-level hooks are NOT configurable from a bundle. The YAML schema has `before_tool_callbacks` / `after_tool_callbacks` (and the
model/agent variants), but they are lists of NAMES looked up in a pre-approved CallbackRegistry (adk_submission/schema.py:253-254,
296-299; adk_submission/registry.py:217-246). `resolve_callback_fields` returns no kwargs when `ctx.callback_registry is None`
(adk_submission/resolvers/callbacks.py:84-85), and the harness calls `compile_submission(...)` without a `callback_registry`
(swegemma/harness/agent_runner.py:616-628), so any callback a bundle names is silently dropped. No bundle-level code, tool wrapper
or tool-response hook exists. What a bundle CAN do is declare a sub-agent as a tool (`agent_tool`, adk_submission/schema.py:91-137).
The harness builds one tool set per task from the task Context (`tools = context.create_tools()`, agent_runner.py:601) and passes
it to the compiler for every agent, so a sub-agent's `submit_patch` is the same function on the same Context. It sets
`ctx.patch_submitted = True` (swegemma/tools/execution.py:111-112), and the runner ends the session on that flag
(agent_runner.py:920). Consequences: (i) the empty-diff guard can be an IN-BUNDLE sub-agent gate. The root gets an `agent_tool` named
`submit_patch` holding `run_command` plus the real `submit_patch`, and it ships unchanged to the scorer. Its enforcement is
the gate model's compliance with a fixed 4-step instruction (temp 0), not code. (ii) The repeat guard can't intercept arbitrary
tool calls: wrapping every tool in a sub-agent would cost an LLM turn per call. So it is PROMPT-LEVEL. Nothing is patched
into our local harness copy. Assumption: the scorer runs the same swegemma 0.2.11 (docs/GOLD_CALIBRATION.md:104). The smoke
(below) verifies the gate end to end in the Kaggle kernel.

**Labels:** repeat guard = PROMPT-LEVEL (its mechanism metric reads as compliance, not enforcement). Empty-diff guard = PROMPT rule
(dec 070 1(b)) PLUS IN-BUNDLE GATE backstop (sub-agent compliance, at most 2 bounces, the 3rd call always submits).
Deviation note for the Director: dec 070 1 expected prompt-only for (b). I kept the gate as well, because dec 070 lists "a
sub-agent via agent_tool" as allowed and the gate ships in the bundle. If the Director rules prompt-only, arm 2 uses v010 with the
gate removed (root gets the harness submit_patch back) and this plan is re-hashed before any run.

## Metrics (all paired against arm 1 on the same 33 ids; computed by one script, codex-reviewed BEFORE arm-2 data exists)
- PRIMARY: resolved discordant pairs A-only (arm 2 resolved, arm 1 not) / B-only, exact two-sided sign test. Resolved = governing
  classifier, same rule as the arm-1 primary (4/33). Also report arm-2 resolved/33 with a Wilson 95% CI.
- MECHANISM 1 (empty patch): rows whose final patch is empty, same definition as arm-1 `empty` (12/33 = 2 timeout + 10 non-timeout).
  Expect <= 4/33. Paired: arm-2-only / arm-1-only empties.
- MECHANISM 2 (repeat, dec 070 item 3): tasks whose max identical consecutive run is >= 5, the dec060 definition and code
  (eval/plan007_arm1_summary.py identical_runs(): consecutive root tool_call entries, same tool + byte-identical args, sort_keys JSON).
  Base 17/33. Expect <= 6/33. Also report the max run, runs >= 3 and total repeated calls (base 366).
- SAFETY (unchanged from dec 069 item 3): test-file edits 0 rows; stray files 0 rows; agent clock <= cap (3.5 min) on every row;
  total wall p90 <= 1.10 x 796.8 s = 876.5 s (arm-1 total_wall p90).
- SAFETY (new, dec 070 item 3, design-note Risk 1): submitted-without-any-test-run = rows with >= 1 root `submit_patch` tool_call and NO
  root `run_command` tool_call before the first `submit_patch` whose `command` arg matches the regex `\bpytest\b|-m\s+unittest\b|\btox\b`.
  The arm-1 base is computed with the same script (one definition for both arms) and committed before arm 2 runs. Rule: arm-2 count <= arm-1 count + 3.
- DESCRIPTIVE: NOT SUBMITTED bounces per task (count of root `submit_patch` calls whose response contains "NOT SUBMITTED"); rows
  ending on the gate's 3rd-call forced submit; tool calls used p50/p90; edit_file failure count; timeouts.

## Decision rule (written before any data)
- SHIP-ELIGIBLE (arm 2 becomes the 31B default draft) iff ALL of: (1) PRIMARY B-only - A-only <= 0, i.e. pass delta >= 0;
  (2) MECHANISM 1 met (empties <= 4/33); (3) MECHANISM 2 met (run>=5 tasks <= 6/33); (4) every SAFETY metric met.
  Chosen per dec 070 item 3: BOTH mechanism metrics are required. A large drop in the repeat metric alone is NOT enough.
- GUARD FAILED (whatever the pass rate): mechanism 1 not met -> the empty-diff guard failed; mechanism 2 not met -> the repeat guard
  failed. Report each separately with the descriptive counts that show why (e.g. bounces ignored, forced 3rd-call submits).
- HARM: B-only - A-only >= 3, or any SAFETY metric missed -> do not adopt; diagnose before any further arm.
- Otherwise NO-DECISION: report, no default change.
- Power caveat (stated in advance): k=1, n=33 detects only large effects. A +-3 swing in resolved count is noise; the sign test needs
  >= 6 of 6 discordants one way for p < 0.05. The mechanism metrics (12 -> <=4, 17 -> <=6) are sized to be readable at this n; the pass
  delta >= 0 condition is a do-no-harm floor, not evidence of a gain.
